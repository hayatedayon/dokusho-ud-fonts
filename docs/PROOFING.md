## 見本を作る

リポジトリのルートで実行します。環境が未準備なら、先に [作り方](DEVELOPMENT.md#作り方) に従って仮想環境と依存パッケージを用意してください。

```sh
.venv/bin/python scripts/build.py
.venv/bin/python scripts/check.py
.venv/bin/python scripts/specimen_page.py
.venv/bin/python scripts/overflow_page.py
.venv/bin/python scripts/proof_page.py
.venv/bin/python scripts/ruby_proof.py   # dist/ruby-trial.html（約40秒）
python3 -m http.server 8000
```

CI の `DokushoUD-proof` 成果物を使う場合は、展開したルートで HTTP サーバーを起動するだけです。フォントのビルド・検査・アップロードは必須で、先に完了させます。見本の生成とアップロードは補助ステップとし、その失敗ではリリースを止めません。生成は３分、アップロードは２分の制限を設けています（ジョブ全体の上限は15分）。生成に失敗した場合は見本のアップロードを省略するため、成果物がないことがあります。CI の該当ステップで結果を確認してください。

## 組版機能

| 用途 | 指定 | 併用の注意 |
| --- | --- | --- |
| 本文 | 和文は既定のベタ組、`kern` は既定で有効 | `font-kerning: none` で欧字カーニングを切れる |
| 横組の見出し | `palt` | `chws`・`halt` を切り、CSS では `text-spacing-trim: space-all` |
| 縦組の見出し | `vpal` | `vchw`・`vhal` を切り、CSS では `text-spacing-trim: space-all` |
| 表・目次の数字 | `tnum` | `pnum` で元のプロポーショナル数字へ戻せる。両方指定すると `pnum` が優先 |
| 和文の引用符 | `ss01`「和文引用符」 | `‘ ’ “ ”` を BIZ UD の全角の字へ戻す。`fwid` 併用時も全角になる。縦組も対応 |
| 欧文用の記号 | `ss02`「欧文記号」 | 日本語文書でも対象の記号を BIZ UDP にする。引用符は対象外なので `ss01` と併用できる。`hwid`・`fwid` 併用時はその幅機能だけを指定した従来の結果を保つ |
| ルビ仮名の試作 | `ss03`「ルビ仮名（試作）」 | 対象は平仮名・片仮名（゠・・を含む）・小書きの片仮名拡張の194字（長音符・繰り返し記号・ゟ・ヿ・結合濁点・半濁点を除く）。ルビだけに指定する。`palt`・`vpal` の詰め量は元の仮名から引き継ぐ |

`ss03` は字形を選ぶ機能です。ルビの大きさと位置はアプリ側で指定します。枠は全角のままなので、ルビをもう一度小さくする機能ではありません。小書き仮名を12%拡大し、線を少し補強した限定的な試作です。完全なルビ専用書体や可読性の向上を保証するものではなく、既存の `ruby` 機能も変更していません。試作字形は原字と同じヒンティングの命令を持ち（8ppem 以上で効きます）、ラスタ比較は [RUBY.md](RUBY.md) にあります。

カーニングの初期値は `scripts/kerning.py` の em 千分率で管理しています。文字の輪郭は変えません。和文の字、全角欧字、`hwid` の半角、`tnum` の数字、縦組用の置換先の字は対象外です。縦組中の横倒し欧字を横組として組む場合はカーニングの対象になります。`check.py` の縦組検査は `vert`・`vrt2` の置換先についての検査です。

## 自動検証

`check.py` は元との輪郭・字幅・ヒンティング・組み方の一致を引き続き検査します。組み方の比較では新しい `kern` を切り、カーニングの検査は別に行います。

- `kerning.PAIRS` で宣言した全ペアをアクセント付き・除外字まで展開し、HarfBuzzで組んだときの送りの差が設定値と一致すること。できたGPOSの実効量もHarfBuzzと突き合わせ、接触検査とは独立に、効かなくなったペアを検出する。
- GPOSの展開は、ゼロ値も含めて最初に一致したサブテーブルを優先すること。Format 1/2の混在、クラス0の暗黙のゼロ、明示的なゼロ、別lookupの処理を小さな表で検査する。実効ペアのインクの隙間が1% em以上あり（水平断面と、斜めを含む輪郭間の最短距離の両方）、等幅の字と縦組を変えないこと。
- `kern` の全入力字が、`hwid`・`fwid`・`tnum`・`vert`・`vrt2` の全置換先と重ならないこと。
- `pnum` が `tnum` を元に戻し、`zero`・`frac` との併用を壊さないこと。
- `ss01`・`ss02` の結果が元の BIZ UD・BIZ UDP と一致し、２つを併用できること。日本語・英語、横組・通常の縦組・`vert=0,vrt2` の縦組で確認する。
- `ss02` と `hwid`・`fwid` の併用で、幅指定だけの場合の字形・送り・配置を保つこと。記号単独・和文中・欧文中、言語指定ja/en、縦横組で全対象字を組んで確かめる。
- `ss02` の横組・縦組の全候補が通常の `locl` 出力・cmap と別の複製であり、輪郭・メトリクス・ヒント・GDEFクラスを保つこと。幅補正の入力として除外できるのも、この複製だけに限る。`ss02` 無効時の `hwid`・`fwid` は、公開1.006の956字×８条件の固定値・字形と配置のハッシュに一致すること。生成側のデータや、現在のフォント同士の比較を基準にしない。
- 試作ルビの194字（縦組の別の字形を含めて1書体235グリフ）が任意の `ss03` でだけ選ばれ、字送りと縦組原点を保ち、行の上下からはみ出さないこと。`palt`・`vpal` との併用でも、元の仮名と同じ送り・配置調整になること。分解した濁音・半濁音、結合濁点・半濁点、`か゚` などの合字との併用でも、記号の字形・送り・位置が変わらず、合字は `ss03` で変わらないこと（`aalt`・`hwid` と併用すると、それらの置き換えが先に働いて `ss03` は効かず、`fwid` と併用すると試作字形になる。この順序と、`aalt` の候補に試作字形が入らないことを検査する）。
- 詰め機能は、`palt`+`chws`・`halt`（縦は`vpal`+`vchw`・`vhal`）の二重詰めを明示的に再現し、排他的な指定がBIZ UDPと同じ結果になること。
- 追加数字に役割ごとの共通CVTゾーンを使う縦方向のヒントを付け、上付き・下付き・分子・分母の数字が8〜24ppemのFreeType３モードで消えず、高さを保つこと。分母はゼロ基準線に揃え、分子・下付き・追加上付き６字もそれぞれ上下端が一致することを、輪郭とラスタで検査する。斜線に接する専用字形も含める。元の上付き¹²³⁴は独立した対照群として元フォントと画素比較し、ヒントを保つ。追加記号はヒントなしのままとする。複数輪郭の数字は、FreeTypeのヒント適用後の全点が同じ縦方向の変形に追従するかも検査し、カウンターだけが動かない不具合を検出する。

## 字の向きと位置の検査（横組・縦組）

`check.py` は `scripts/glyph_reference.py` で、字の向きや置き換え先の取り違えを４書体すべて、言語指定ja/en、横組・縦組で検査します。基準は Noto Serif/Sans CJK JP の低解像度の形と位置を記録した `tests/fixtures/glyph-reference.json` で、CIに Noto は不要です。

- 全字（漢字・ハングルを除く）で、そのままより反転・180度回転した形が基準に近ければ失敗する。
- BIZ UD・BIZ UDP と同じ字はデザインの差として位置の比較から除き、読書 UD で作った・変えた字の位置を基準と比べる。
- `vrt2` の欧字が、横組の字を右へ90度回した形であること。
- 上付き・下付き・分数・`tnum`・`hwid`・`fwid` の数字が、横組・縦組（`vert`・`vrt2`）とも同じ数字の形であること。
- 縦組の `“ ”` は `〝 〟` と同じ形、`‘ ’` はその 1 画で、送りは全角（`spec.VERTICAL_MINUTES`・`check_vertical_minutes`）。`“ ”` は英語の中でもミニュートの形のまま。欧字の組（縦組で横に倒した `It’s` など）の `‘ ’` は、横に倒した字（用字系 `latn` の `vert`・`vrt2`）。`ss01` の縦組は BIZ UD の引用符に戻り、`‘ ’` は Noto と同じ向きに入れ替えてある（`spec.VERTICAL_SWAPPED_QUOTES`）。
- 既知の例外は `glyph_reference.py` の `KNOWN_ORIENTATION` などに理由つきで置く。

基準を更新するには、Noto を入手して次を実行します。結果の差は必ず確認してください。

```sh
python3 scripts/glyph_reference.py record NotoSerifCJK-Regular.ttc NotoSansCJK-Regular.ttc
```

## 1.010 の実環境の確認表

`dist/additions.html` と `dist/additions/*.png` は追加字の FreeType 画像です。12・14・16pxの実寸と同じ画素の４倍、96pxを４書体で見比べます。𠮷と吉の違い、土の下の横画の長さ、口の形、〱・〲の接合と濁点、縦組で前後の仮名２字分を使うことを確認します。画像を自動で作っても、目視で確かめたことにはなりません。

補助 CI `Native shaping proofs` は CoreText／DirectWrite の同一資料を保存します。各成果物を展開し `dist/native/index.html` を開き、フォントの SHA-256 が一致するものを比較します。JSON の単位は24px、字形の ID は同じフォントの中で比べます。縦組の横倒し欧文などはエンジンの用字系分割も影響するため、送りと画像を合わせて確認します。`kern` と `kern-off` の差、アクセント付きの字と `Ť` の除外、`vert` の向きと追加字を見ます。縦組の `〱 〲 ⸺ ⸻` の送り（2 em・2 em・2 em・3 em）は、CI が合否を判定します。エンジンごとの違いは [1.008 の確認記録](proofing-records/1.008.md) と [1.009 の確認記録](proofing-records/1.009.md) にあります。

### 1.010 の送りの補正と、Safari の既知の制限

Safari 27.2（macOS 15.8.2）で `writing-mode: vertical-rl` または `vertical-lr` と `text-orientation: upright` を指定すると、縦組の `⸺`（U+2E3A）・`⸻`（U+2E3B）の送りが1 emになり、次の字に重なります。`あ⸺い`・`あ⸻い` は全体が3 emで、期待する4 em・5 emに足りません。4書体とも、`font-feature-settings` の指定なし・`"vert" 1`・`"vrt2" 1` で同じです（補助 CI run 44199462703・44211421561）。1.009から同じで、1.010 でも既知の制限として残っています。

1.010 では `text-orientation: mixed` にすると、この2字の送りは2 em・3 emになり、次の字との重なりを避けられます（同じ環境で測定）。字の向きも変わるので、用途に合わせて選んでください。iOS Safari は未確認です。

1.010 の `wide_cursX` 実装（commit `7895043`）は、`SOURCE_DATE_EPOCH=1794919244` でビルドし、run 44199462703 で4書体を検証しました。1.009（run 44195381228）の標準の結果と比べると、Safari 27.2 の mixed の vertical-rl・vertical-lr（`normal`・`"vert" 1`・`"vrt2" 1`）では、1.010 は全4書体で `あ+字+い` の合計が4・4・4・5 em でした（1.009 は3・3・3・3 em）。Safari の `text-orientation: upright` は `〱`・`〲` が4 em、`⸺`・`⸻` が3 emです。後者は1.009と同じで、既知の制限として残します。sideways も測定しましたが、1.009 の標準成果物に同条件の行がないため、その向きの差分比較には含めていません。Safari の測定は送りの長さと文字範囲を測ったもので、OS標準のフォント描画 API によるピクセル単位のインク比較ではありません。

この補正を採用しました。1.009 のビルドと比べると、TTF は4書体とも `GPOS` の中身だけが変わり、それに合わせて `head` のチェックサムが変わりました。`curs` の XAdvance を1段目の縦字形に追加し、既存の空白字の値は維持しています。glyph order、`glyf`、`cmap`、`hmtx`、`vmtx` は一致し、他の OpenType 機能も不変です。`scripts/check.py` は `ok: 4 fonts` でした。補助 CI run 44199462703 は総合 success（Edge / CoreText / DirectWrite success、Safari advisory failure）。Safari で upright を指定したときのダッシュ2字の重なりは、1.010 でも残ります。

### Hayate Reader での確認（2026-11-18）

統合候補（Build run 44297371650 の WOFF2 4本）と 1.009 を、Hayate Reader のコミット `364ac9b` で比べました。Linux の WebKitGTK 2.52.6 で、縦組／横組、明朝／ゴシック、明るい／暗いテーマ、800×600／1200×800 の16条件を、本文18 CSS px、行送り1.8、倍率1で撮影しました。通常の読書画面では16条件すべてで差分画素が0でした。縦組の `〱 〲 ⸺ ⸻` は両版とも36・36・36・54 pxの送りで、次の字と重なりませんでした。

ルビ仮名の試作は、候補版の WebView に比較用の要素を追加して確かめました。同じ仮名を26 CSS pxで並べ、一方に `"ss03" 1` を指定しました（縦組は両方に `"vert" 1`）。4書体×縦横組の8条件で、194字すべてが `ss03` を指定すると試作字形になりました。

### Hayate Reader で確かめる

主な利用先の EPUB リーダー Hayate Reader（別リポジトリ）は、Tauri 2 の WebView で本文を表示します。確認する字を入れた EPUB を用意し、Reader で開いて撮ります。Reader の道具は同リポジトリの `AGENTS.md` の「動作確認」にあります。

1. 上の確認文（２つ）を横組と縦組で書いた EPUB を作ります。`lang="ja"` を書いた章と、言語を書かない章（Reader が書誌の `dc:language` を補います）を分けます。`scripts/agent/fixtures.js` の見本の本を手本にでき、`--book` にはパスも渡せます。
2. `node scripts/agent/app.js start --book <EPUB>` で起動し、`screenshot` で撮ります（`--selector` で要素だけ）。起動と操作は Linux（WebKitGTK）と Windows（WebView2）で使えます。macOS（WKWebView）には外から操作する口が無いので、手で開いて撮ります。
3. Reader に同梱の読書 UD は同梱時に固定したリリースのファイルです。公開前の候補版を試すときは、端末にそのフォントを入れ、表示パネルの 4 つ目のタイル（この端末のフォント）で選びます。
4. 字形は等倍以上に拡大して見ます。フォントの SHA-256、Reader の版、WebView の版、設定、画像を記録します。
