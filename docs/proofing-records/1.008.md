## 補助 CI（CoreText・DirectWrite）の確認（2026-11-09）

補助 CI `Native shaping proofs` は CoreText／DirectWrite の同一資料を保存します。各成果物を展開し `dist/native/index.html` を開き、フォントの SHA-256 が一致するものを比較します。JSON の単位は24px、字形の ID は同じフォントの中で比べます。縦組の横倒し欧文などはエンジンの用字系分割も影響するため、送りと画像を合わせて確認します。`kern` と `kern-off` の差、アクセント付きの字と `Ť` の除外、`vert` の向きと追加字を見ます。2026-11-09 に PR #1 の CI で、CoreText（macOS 15.8.2）と DirectWrite（Windows Server 2025）の両方が合格しました。４書体×45条件の組版と描画で別フォントへのフォールバックがなく、句読点の単独ペアの送りも宣言値と一致しました。

CI でわかったことは次のとおりです。

- どちらのエンジンでも、横組の `ALWAYS_UDP` の17字は BIZ UDP の字幅になり（`“ ”` は0.5 em、`—` は1 em）、`locl` が既定で効いています。
- どちらのエンジンでも、`locl=0` を指定した `locl-off` は字形 ID と字幅が通常と同じで、`locl` が効かない環境の再現にはなりませんでした。
- DirectWrite では、`kern` を切っても字幅が変わりませんでした。CoreText では切ると広がります（明朝 Regular で626.12から652.75）。
- DirectWrite の縦組では `“ ”` が半角の字幅で横倒しになり、`〝 〟` の形になりません。字形 ID と字幅から判断したもので、画像は見ていません。CoreText の縦組では全角の字幅でした。

## Chrome と PDF の確認（2026-11-10）

Chrome と PDF の確認（2026-11-10）でわかったことは次のとおりです。確認には 1.008 のフォント（`4e813c1` からビルド）を埋め込んだ一時の確認用ページを使いました。

- Windows の Chrome 156 で、４書体とも `line-height: normal` の1行の高さが1.5 em、`——` が2 em、`“` が0.5 em、`T.` のカーニングが宣言値（明朝 −0.070 em、ゴシック −0.055 em）になりました。`𠮷` も読書 UD の字で組まれました。
- 縦組では、`〱 〲` が２字分の高さの１字になり、`“ ”` と `‘ ’` は `〝 〟` の形になりました。横組の `〱` は１セルに縮めた見本で表示されます。
- Chrome で保存した PDF には４書体が埋め込まれ、Chrome の PDF 表示で「𠮷野」を検索できました。Word と InDesign から書き出した PDF と、別のビューアでの表示は確かめていません。

## Hayate Reader（WebKitGTK）の確認（2026-11-15）

> 注記（2026-11-16）: この節は、Reader に同梱の 1.008（v1.0.8）のフォントでの確認です。1 つ目の「期待と違った結果」のうち、`vert` を指定した最小の HTML で縦組の送りを測った部分だけは、2 段の置き換えを入れた候補版のフォントでの測定です（1.008 の値は括弧の中に書いてあります）。「未公開の変更」は、1.009 の変更のことです。

Hayate Reader（WebKitGTK）の確認（2026-11-15）でわかったことは次のとおりです。

- 環境は Ubuntu 26.04.1 LTS、WebKitGTK 2.52.6（`libwebkit2gtk-4.1-0 2.52.6-0ubuntu0.26.04.1`）、Hayate Reader の開発版（当時）です。Xvfb の仮想画面（1920x1080x24）に、1200x800のウィンドウ、単ページ表示、行送り1.8で表示しました。フォントは Reader に同梱の v1.0.8 の WOFF2 の４つで、SHA-256 は Reader の記録と一致しました。システムに BIZ UD・読書 UD は入っておらず、Noto CJK は入っています。
- 測り方は章の文書で `Range.getBoundingClientRect()` の値を em に直しました。WebKitGTK は字の送りを整数 px に丸めるので、値には ±0.5px の誤差があります。期待値は WOFF2 を fontTools で読み、`locl` の後の字形の `hmtx` と GPOS の `kern` から出しました。確認用の EPUB は４冊（書誌の言語が ja と en、横組と縦組）で、章は `lang="ja"`・言語なし・`lang="en"`・行送り・カーニング・ルビ・拡大（96px）です。明朝とゴシックを32pxと18pxで測りました。
- 選んだ同梱フォントは Regular・Bold とも読み込まれました。`𠮷`・`〱`・`〲` を含む15字は同梱フォントの字で出ました（canvas の画素を、Noto を後ろに付けた場合、Noto だけの場合と比べました）。
- `ALWAYS_UDP` の17字の字幅は `locl` の後の値と合いました（差は最大0.39px）。`“ ”` は0.5 em、`—` は1 em、`−` は0.84 em、`°` は明朝0.37 em・ゴシック0.35 em、`½` は明朝0.94 em・ゴシック1.0 em、`‼` は0.88 em です。`lang="ja"`・言語なし・`lang="en"` の３つの章で、書誌が ja でも en でも、17字の字幅は同じでした。言語を書いていない章には、Reader が本の書誌の言語（ja の本は `ja`、en の本は `en`）を補っていました。
- カーニングは、`T. V, W. Y, P. F, r. y, v. w,` の1行の幅が `font-kerning: none` との差で明朝0.555 em、ゴシック0.419 em でした（期待は0.555 em と0.420 em）。縦組の横倒しでも同じです。組ごとに見ると、差が見えたのは `T.` だけで（0.062 em、期待は0.070 em）、`W.`・`r.`・`v.` は丸めで見えませんでした。
- 行送りは、computed の `line-height` が設定どおりでした（57.6px、32.4px、52.8px）。
- 縦組の `“ ”` は `〝 〟` の形で、全角・正立でした（３つの言語の章、両書体）。縦組の `‘ ’` は全角でした。
- ルビは縦組・横組とも付きました。Reader は `ss03` を指定していません。
- 期待と違った結果が３つあり、原因が分かりました。
  1. 縦組の `〱`・`〲` の送りが1 em 前後になりました（`vmtx` は2 em＝4096/2048 ですが、Reader で `Range` の高さは `〱` が96pxで1.000 em、32pxで1.031 em、18pxで1.056 em、`あ〱い` は96pxで3.000 em）。原因は WebKitGTK が縦組の送りに `vmtx` を使わず、正立する字を、`vert`・`vrt2` で置き換わった字形も含めて、常に1 em で送ることです（横向きに回される字は `hmtx` で送ります）。Reader の CSS を通さない最小の HTML（明朝・ゴシック、16・18・32・96px）でも、`〱`・`〲` は1 em でした。Reader が Linux で付ける `font-feature-settings: "vert" 1` を指定すると、`⸺` も `⸻` も1 em になります（`vert` を付けなければ `hmtx` の2 em・3 em です）。1.008 のフォントでは、２字分の高さの字形が１字分の送りに入って、続く字に重なります。フォントの側では縦組の `vert`・`vrt2` を２段にして、同じ輪郭と縦送りの字と空白の字に置き換えます（未公開の変更。[FONTLOG](../../FONTLOG.txt) の次期版の項。補助 CI での実験の結果は「縦組の `〱 〲` の送りの実験」）。同じ最小の HTML（明朝・ゴシック、Regular・Bold、40px、縦組）で測ると、`vert` を指定したとき、`〱`・`〲` と `⸺` は送りが2 em、`⸻` は3 em で、次の字はそれぞれ2 em・3 em の位置から始まり、スクリーンショットでも重なりませんでした（1.008 では、`〱`・`〲`・`⸺`・`⸻` とも1 em）。指定しないとき（WebKitGTK は `vert` を自分では効かせません）は、1.008 も新しいフォントも、`〱`・`〲` は cmap の１セルの字形が1 em で出て（２セルの字形にはなりません）、`⸺`・`⸻` は2 em・3 em の送りですが、横線のまま縦組の列に正立して描かれます。Reader 本体での再確認はまだしていません。
  2. 隣り合う行の間隔が行送り57.6pxに対して57px、32.4pxに対して32px、52.8pxに対して52pxでした。原因は WebKit が行の高さを整数ピクセルに切り捨てて組むことで、フォントの問題ではありません。最小の HTML で、読書 UD明朝・ゴシックとシステムの serif のどれも、横組・縦組とも同じでした。600行の段落の block サイズは34200px＝600×57で、`line-height: 57.5px` や `57.25px` でも57pxでした（computed の値は指定どおりです）。
  3. 横組の `〱` の幅が18pxで1.056 em、32pxで1.031 em、96pxで1.000 em でした。原因は `Range` の矩形の丸めによる見かけで、`あ〱い` の3字の全幅は18pxで54px、32pxで96px、つまり3.000 em でした（`hmtx` は1 em）。フォントの問題ではありません。
- `locl` を切った対照では `font-feature-settings: "locl" 0` を指定すると、単独で組んだ字（明朝・ゴシック、横組・縦組）が、`“ ” ‘ ’` は1.0 em、`—`・`−`・`½`・`‼`・`⁇` は0.5 em、`°` は1.0 em に戻りました。WebKitGTK では `locl` を切った環境を再現できます。CI でわかったとおり CoreText と DirectWrite では `locl=0` を指定しても変わらなかったのと対照的です。ただし縦組の文章の中の `Range`（32px）では、`“ ” ‘ ’` 以外（`—`・`−`・`°`・`½`・`‼`）が `locl` を切っても変わらなかったので、この対照は縦組では単独の字で読んでください。
- 確かめていないことは、実機の画面での見た目（仮想画面だけ）、拡大した画面の目視（スクリーンショット116枚のうち目で見たのは6枚で、くの字点の接合と濁点の形は拡大して見ていません）、見開き表示、`ss01`・`ss02`、行末の `‐`、`halt`・`chws`、リリースビルドです。
